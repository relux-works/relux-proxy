# Evidence-led packet, transport, memory, and energy tuning

## Description
Establish a reproducible M3 baseline and tune packet, HEV, lane, window, rekey, QUIC, reconnect, memory, CPU, and energy parameters only from named physical-device evidence, preserving fixed memory ceilings, routing and DNS safety, and before-and-after regression records.

## Scope
In scope: benchmark protocol and workload definitions; device, OS, source, dependency, profile, network-condition, and traffic metadata; physical footprint, peak, advisory available memory, CPU, energy, packet and syscall rate, throughput, time-to-first-byte, DNS latency, RTT, queues, windows, channels, HEV sessions and caches, lane count, reconnect overlap, drops, errors, and cleanup; MTU 1500, 4096, and 8500; socket buffers and effective values; adaptive batches; HEV low-memory baseline; one, two, and four lanes; 32 KiB, 64 KiB, and capped BDP windows; rekey and Auto QUIC thresholds; watermarks and retry; Instruments bottleneck analysis; before-and-after tuning; final physical resilience matrix. Out of scope: unmeasured constants, private APIs, destination or query logging, weakening correctness or leak gates for throughput, forking HEV without material evidence and regression coverage, unsupported device claims, or release marketing benchmarks.

## Acceptance Criteria
1. A task-scoped protocol defines reproducible workloads, network impairments, warmup, duration, samples, statistical comparison, pass or fail rules, metadata, raw artifact references, redaction, and regression thresholds. 2. Low-overhead bounded instrumentation reconciles packet, transport, DNS, relay, lane, memory, CPU, energy, error, and cleanup counters without payloads, destinations, query names, or high-cardinality identifiers. 3. Untuned iPhone and Mac baselines cover required MTUs, lane counts, window profiles, traffic shapes, concurrency stages, loss and latency, lifecycle, and the provisional HEV configuration. 4. Each accepted parameter change has before-and-after evidence and preserves byte correctness, latency bounds, route safety, zero ordinary DNS fallback, bounded queues, and the extension memory ceiling. 5. The 25 to 30 MiB steady-state target is reported as measured engineering evidence rather than an Apple guarantee, with peak, reconnect overlap, available-memory samples, and any device variance. 6. A HEV fork is approved only if Instruments identifies bridge copies or syscall rate as a material bottleneck and a minimal upstream-trackable change demonstrates meaningful improvement with regression coverage. 7. The final named-device matrix passes lane congestion, rekey, memory pressure, path changes, NAT64, sleep and wake, captive, QUIC, and both route modes or records explicit red rows and blocking follow-up work, and publishes accepted baselines and thresholds.
