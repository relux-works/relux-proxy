# Production SSH lane pool and congestion-aware scheduler

## Description
Build a bounded pool of two to four authenticated SSH connections to one approved host, reserve the mandatory control lane, assign each new flow to an eligible general or optional bulk lane from congestion evidence, pin the flow until close, and recover lane-local failures without leaking traffic or multiplying memory.

## Scope
In scope: control, general, and optional bulk lane topology; shared verified identity and profile generation; lane lifecycle and admission; health, writable-window, queued-byte, RTT, channel-count, and rekey signals; control and DNS priority; best-effort bulk classification; immutable flow pinning; memory-pressure gating; lane-local recovery and degraded capability handoff; privacy-safe observability; deterministic fault tests; physical one, two, and four lane loss and head-of-line measurements. Out of scope: SSH engine selection, changing packet framing, implementing channel-window or memory-watermark algorithms owned by STORY-260715-1zzt0c, migrating live byte streams, relay wire protocol, ProxyJump, SFTP, interactive shells, or application-specific routing.

## Acceptance Criteria
1. One mandatory control lane starts first and optional general or bulk lanes open only after identity, server-limit, and memory admission checks. 2. Every lane proves the same approved host identity and credential generation, and any mismatch closes that lane before channels open. 3. New flows are assigned from documented congestion and policy inputs, remain pinned until close, and Lane D never retroactively adopts an existing flow. 4. Control, relay, and latency-sensitive DNS remain serviceable under general or bulk congestion within recorded latency bounds. 5. Rekey and failed-lane states stop new assignment on the affected lane, preserve valid existing channel state where possible, and route control-lane loss through an explicit degraded or recovery transition without DNS or UDP leakage. 6. Queues, lanes, and channels stay inside configured ceilings and soft memory pressure suppresses optional capacity. 7. Deterministic tests and physical iPhone and Mac trials at one, two, and four lanes record loss, latency, throughput, queues, windows, channels, memory, CPU, errors, and cleanup and demonstrate measured head-of-line improvement without resource growth.
