# M0 in-process SSH engine comparison and selection

## Description
Compare a minimal, upstream-trackable ReluxNIOSSH fork with libssh2 behind one spike transport contract and select an in-process engine only after one candidate passes the complete Apple-target, host-verification, authentication, direct-tcpip, exec, window, rekey, compatibility, backpressure, cancellation, lifecycle, and memory matrix.

## Scope
In scope: pinned candidate revisions and licenses; iOS and macOS packet-tunnel-compatible static or source integration; raw host-key evidence; Ed25519 and approved fallback authentication; direct-tcpip and bidirectional exec channels; bounded writes; per-channel initial windows and adjustment policy; client byte and time rekey plus server rekey; keepalive, cancellation, metrics, and error mapping; current and supported older OpenSSH profiles plus the real relux server; hundreds of channels; at least 5 GiB mixed traffic; one, two, and four raw SSH connections; loss, reconnect, and descriptor tests; memory comparison; engine ADR and fork maintenance plan. Out of scope: SFTP, interactive shells, agent or X11 forwarding, password prompts, ProxyJump, production lane scheduling or flow migration, QUIC policy implementation, remote relay implementation, and weakening a failed gate to preserve a preferred candidate.

## Acceptance Criteria
1. Both candidates build in the macOS and iOS packet-tunnel target configurations, with pinned revisions, licenses, integration constraints, and reproducible build commands recorded. 2. One common conformance harness obtains raw host-key evidence before acceptance and exercises Ed25519 plus an approved fallback against current OpenSSH, documented older profiles, and the real relux host. 3. Candidate evidence covers independent direct-tcpip and bidirectional long-lived exec channels, early close and half-close, bounded backpressure, cancellation, network loss, reconnect, and no task, channel, socket, or descriptor growth across repeated cycles. 4. Initial receive windows and WINDOW_ADJUST behavior are configurable per channel; tests cover 32 KiB, 64 KiB, and capped bandwidth-delay-product profiles without multiplying a large default by maximum sessions. 5. Client byte and time thresholds and server requests survive at least 5 GiB of simultaneous direct-tcpip and exec traffic, with lane-local failure evidence. 6. Hundreds of concurrent channels and one, two, and four connection trials remain within the extension memory budget and record device, OS, revisions, algorithms, traffic, loss and latency, windows, queued bytes, CPU, physical footprint, peak, and failures. 7. A decision record selects only a candidate that passes every required gate, documents rejected results and residual risks, and routes a red primary candidate to the alternate rather than weakening criteria.
