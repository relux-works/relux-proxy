# Generated Apple multi-target project foundation

## Description
Replace the single-target SwiftPM-only project shape with a reproducibly generated Apple workspace foundation that can embed iOS and macOS packet-tunnel extensions while preserving the currently shipped macOS SOCKS application until a separate migration decision retires or replaces it. Establish thin platform adapters, a shared ReluxTunnelCore boundary, native dependency seams, a fast macOS harness, and relay target placeholders without implementing production tunnel behavior.

## Scope
In scope: current-state and migration inventory; Tuist-versus-alternative and deployment-target evidence; target and configuration graph; iOS and macOS host and packet-tunnel targets; ReluxTunnelCore Swift package; ReluxTunnelHarness CLI; portable relux-relay and protocol-test target shells; signing configuration seams; pinned native dependency integration strategy; clean generation, build, and test verification; legacy SwiftPM and release-path preservation; developer documentation. Out of scope: production packet forwarding, SSH engine selection, UDP relay protocol implementation, profile UX migration, full release automation, App Store submission, and retirement of the existing system-SSH app.

## Acceptance Criteria
1. An architecture decision records the chosen generator, exact supported deployment targets, target graph, module ownership, dependency direction, configuration strategy, and reasons against viable alternatives. 2. Clean generation produces buildable ReluxProxyMac, ReluxProxyMacTunnel, ReluxProxyIOS, ReluxProxyIOSTunnel, ReluxTunnelCore, ReluxTunnelHarness, relux-relay, and protocol-test targets with deterministic identifiers and schemes. 3. Both providers are thin adapters that depend on shared core contracts and do not duplicate packet, SSH, relay, lifecycle, or memory state machines. 4. Native Swift and C dependencies can be pinned, licensed, and linked without dynamic-library or App Store extension violations. 5. Credential-free CI or local verification builds every target and runs shared tests; signed physical-device configurations consume Gate P0 identities without committing secrets. 6. The existing SwiftPM tests, manual SOCKS app build, defaults, and release path remain reproducible until an explicit migration decision says otherwise. 7. Developer documentation explains generation, target ownership, signing inputs, artifact locations, and how to run the harness.
